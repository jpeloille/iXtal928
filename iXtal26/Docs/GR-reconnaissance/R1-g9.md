6. La sonde SVGA lit 75 champs de `svga_t` pour l'ET4000, banques comprises ; de `et4000_t` lui manquent l'état et la
   commande du RAMDAC (`ramdac.state`, `ramdac.ctrl`).

### 1.5 Ce que la ROM `et4000.bin` offre (désassemblage par `objdump -m i8086`, hors dépôt ; déduit)

- **En-tête** : « TsengLabs Int'l ET4000 BIOS, Date : 04/07/93 », « V8.01X ». Aucune chaîne « VESA » (G9.3 l'a mesuré).
- **Le 1024×768** : la liste des modes de 256 couleurs, `13h 2Dh 2Eh 2Fh 30h 38h`, en C000:0D8C (lue par `mov bx,0D8Ch`,
  `mov cx,6`) ; deux tables de paramètres de 64 octets à 128 colonnes × 48 rangées, C000:71C0 (GR5 = 00h, 16
  couleurs, le mode 37h) et C000:7200 (GR5 = 40h, 256 couleurs, le mode 38h ; 768 Ko, la carte en a 1 Mo). CR00 = 99h,
  CR06 = 2Fh et CR07 = F5h : 158 caractères × 817 lignes, 768 affichées — le minutage entrelacé du 8514 (44,9 MHz,
  35,5 kHz). Ce que le BIOS pose dans CR34 (l'horloge CS2) et CR35 (bit 7, l'entrelacé) : inconnu, à relever.
- **Le HiColor** : INT 10h AH = 10h, AL = F0h, F1h, F2h, aiguillés en C000:238B vers 79E8h (fixer un mode HiColor),
  7CCEh (lire le type de RAMDAC) et 7CDBh (lire le mode). 10F0h exige un type non nul (79EBh), accepte BL = 2Dh, 2Fh
  (512 Ko), 2Eh, 30h (1 Mo) et, pour un type 2 ou plus, 13h ; BL = FFh (16 bits) ou FEh (24 bits), BH = 2Dh-2Fh, selon
  une table par type en C000:79DE (`00 00 00 01 01 03 01 02 01 01`).
- **La détection du RAMDAC (7CE0h)**, tracée à la main sur `vid_unk_ramdac.c` :
  - commande et masque relus, puis E0h et 60h écrits par l'IPF et relus ; l'ancienne commande remise ;
  - en mode PCem, deux lectures après l'IPF rendent la commande puis le masque : le chemin de 7D37h. FFh y est écrit
    armé : PCem le jette au masque (`vid_unk_ramdac.c:24`, PB-100 (c)) et la commande relue n'est pas FFh : **type 4**.
    Une puce qui prendrait FFh pour commande rendrait le type 3.
  - en mode matériel, l'IPF de PB-229 tient (`vid_unk_ramdac.cs:118-120`) : la seconde lecture rend encore la
    commande, et le BIOS prend 7D4Ah (les registres étendus par l'index de 3C8h, 7DB7h) : **type 2**.
  Conséquence : sous 10F0h BL = FFh, le mode PCem passerait en 16 bits, le mode matériel refuserait ; sous BL = 2Eh,
  les deux poseraient un mode, la commande du RAMDAC écrite selon le type (7C0Bh, 7E54h). À mesurer : c'est le
  premier relevé du banc HiColor. G13.9e l'a déjà vu au POST (« sous PB-229 seul, vingt instructions de plus »).

## 2. Ce qui reste, et les étapes proposées

L'ordre suit PLAN.md (GR.0 avant GR.1) ; GR.1a à GR.1e ne dépendent pas de GR.0 (la sonde SVGA hache déjà `buffer32`
et `pallook`), GR.1f et GR.1g en dépendent. Une série entière par étape qui change l'émulateur ou l'oracle ; un
sous-ensemble ciblé sinon. Le mode PCem reste identique à l'unité : aucune de ces étapes ne touche une ligne transcrite
hors des commentaires (GR.1i).

**GR.1a — La sonde de l'ET4000.**
- Contenu : `h_et4000_probe` dans le harnais (`vid_et4000.c` est lié, `et4000_t` se lit en incluant le `.c` comme
  `harness_tvga.c`), son pendant C# dans `vid_svga.Probe` : `et4000.banking`, `et4000.ramdac.state`,
  `et4000.ramdac.ctrl`, nommés dans `VgaProbe.Fields` ; ABI 57 → 58.
- Portes et preuves : les cinq portes de l'ET4000 (`series.sh:293-299`) comparent les champs neufs ; `vga-probe` et
  `abi` suivent.
- Contrôles négatifs : côté C#, 3C8h qui ne remet pas `state` à zéro → ET4BANC rouge à la sonde (et non au diff) ;
  `banking` non rangé → rouge.
- La série : les cinq portes, mêmes comptes, sonde plus large ; `abi`.

**GR.1b — L'ET4000 sous DOS sur l'ami486, et sa ROM sur le 8088.**
- Contenu : `bd-ami486-et4000-dos` sur le patron de `:132` ; `et4000ax` dans `VgaProbe.Card` ; `vga-probe` sur
  `ibmpc` et `ibmxt` (oracle seul) et un désassemblage récursif des chemins d'init et d'INT 10h, comme M19.
- Portes et preuves : une porte neuve ; la mesure du 8088 dite dans VERIFICATION (le vecteur d'INT 10h en C000h, le
  mode 3 posé, l'invite), sans porte si la ROM ne tourne pas.
- Contrôle négatif : SR7 sans son bit 2 forcé côté C# (celui de G9.3) → la porte DOS rougit.
- La série : une porte de plus.

**GR.1c — ET4BANC jusqu'au 1024×768 en 256 couleurs.**
- Contenu : le script d'ET4BANC garde ses relevés, les imprime en texte, attend une touche, puis pose le mode 38h,
  remplit les douze banques de 64 Ko, relit CR34, CR35 et 3CDh, et sort dans ce mode. Le motif imprimé avant la touche
  garde des attendus octet par octet ; `@vram` prend l'empreinte du mode final, comme BLTBANC.
- Portes et preuves : `bd-ami386dx-et4-banc` recompté, la sonde voit le 1024×768 (`video_res_x`, `bpp`, `buffer32`) ;
  `banc-et4banc` et `-materiel`, attendus réécrits, chaque octet neuf expliqué (PB-220 et PB-226 en mode matériel).
- Contrôle négatif : `rowoffset` de 38h faussé côté C# (CR13 lu sur 7 bits) → la sonde rougit.
- La série : un compte qui change (`bd-ami386dx-et4-banc`), deux attendus réécrits.

**GR.1d — Le banc HiColor (ET4HBANC).**
- Contenu : 10F1h (le type relevé), 10F2h ; le RAMDAC armé, FFh écrit, la commande et le masque relus (PB-100 (c)) ;
  40h puis E4h (32 bits), 60h (24 bits), chacun relu ; puis 10F0h BL = 2Eh, une touche, et la sortie en HiColor. Si un
  mode refuse 10F0h, le banc le relève et pose A0h par l'IPF après le mode 2Eh (le chemin d'ET4BANC).
- Portes et preuves : `bd-ami386dx-et4h-banc` (mode PCem contre l'oracle : type 4 attendu, déduit) ;
  `banc-et4hbanc` et `-materiel` (type 2 attendu, déduit ; le chemin de 10F0h diffère, expliqué).
- Contrôles négatifs : côté C#, FFh armé pris pour commande en mode PCem → le diff rougit à la lecture du type ; le
  décodage de 40h rendu à 24 bits → la sonde (`bpp`) rougit.
- La série : trois portes neuves.

**GR.1e — EGABANC avec AND et OR, et les bancs qui finissent dans leur mode** (PLAN.md:327-328).
- Contenu : GR3 = 08h et 10h, chacun sur un verrou connu, relus ; EGABANC finit en 10h et HERCBANC en graphique, après
  une touche, leurs relevés imprimés avant.
- Portes et preuves : `bd-pc-ega-banc` et `bd-pc-herc-banc` recomptés ; quatre attendus réécrits ; `@vram`.
- Contrôle négatif : AND et OR échangés dans `ega_logic` (`vid_ega.cs:1039`) → le diff rougit au relevé.
- La série : deux comptes, quatre attendus.

**GR.1f — Les clés sous boot-diff : 64 Ko, le moniteur mono, l'ambre** (après GR.0).
- Contenu : quatre `.cfg` de porte (`[EGA] memory = 64` ; `[EGA] monitor_type = 74`, l'ambre mono ; `[MDA]` et
  `[Hercules] display_type = 4`) ; `r9-videocfg` étendu à `memory` et `display_type` hors liste.
- Portes et preuves : POST et DOS sur le 5150 et l'AT pour l'EGA de 64 Ko et mono (3Bx sous le diff) ; POST du 5150
  pour la MDA et l'Hercules en ambre ; EGABANC sur 64 Ko ; la sonde de GR.0 voit `pallook` et `buffer32`.
- Contrôles négatifs : le `^ 0x60` retiré côté C# → le diff rougit au premier accès en 3B4h ; l'ambre faussé dans
  `cgapal_rebuild` côté C# → la sonde rougit ; `memory` lu 128 → la sonde (`vrammask`) rougit.
- La série : huit à dix portes neuves, seize essais `r9` de plus.

**GR.1g — MDABANC** (après GR.0).
- Contenu : `tools/mdabanc/`, l'interprète de HERCBANC ; R0-R17 écrits et relus ; INT 10h AH = 01h, CX = 0607h, puis
  R10 et R11 relus ; R4 = 99h ; 3BAh échantillonné (OU, ET, la durée d'une trame en tours : PB-102) ; 3B8h ; un écran
  aux attributs 01h, 07h, 08h, 70h, 80h. Après la touche, l'état final : R8 = 03h, R9 = 13h, le curseur caché.
- Portes et preuves : `bd-pc-mda-banc` (la sonde de GR.0 voit `sc`, l'entrelacé et les rangées 16-19 de PB-96) ;
  `banc-mdabanc` et `-materiel` : 0Bh 0Ch contre 06h 07h, 3BAh (PB-224), la trame (PB-102). PB-96 en mode matériel ne se
  voit qu'aux pixels : une directive d'empreinte de l'image en fin de script (l'empreinte de `ReportFramebuffer`,
  `BootTest.cs:308`), stable le curseur caché et sans attribut clignotant (déduit).
- Contrôles négatifs : le Turbo XT retiré du mode PCem → le diff rougit à la relecture de R11 ; `& 15` au lieu de
  `& 7` dans l'entrelacé → la sonde rougit ; `fontdatm` lu `sc & 15` en mode PCem → la sonde (pixels) rougit.
- La série : trois portes neuves.

**GR.1h — La couverture comptée.**
- Contenu : la méthode de M15, sur une copie jetable du worktree (un script hors dépôt) : un compteur par méthode,

**GR.1i — La relecture contradictoire.**
- Contenu : cinq tranches disjointes, chacune avec un relecteur qui la lit et un second chargé de réfuter ses constats

- Preuves : les constats corrigés ; M2 identique (des commentaires seuls) ; un sous-ensemble ciblé (`recensement`,
  les portes vidéo), pas de série entière si seuls des commentaires changent.

## 3. Les risques

- **GR.0 d'abord** : sans la police, `cgapal_rebuild` et les hachages de l'image dans l'oracle, l'ambre, PB-96 et
  l'entrelacé passent au vert sans être comparés. GR.1f et GR.1g n'ont de sens qu'après.
- **La détection du RAMDAC** (§ 1.5) est déduite d'une trace à la main : si le type relevé diffère, le banc HiColor
  suit d'autres chemins ; aucun des deux types n'est celui d'une Sierra réelle, inconnue (décision n° 14).
- **Le mode 38h** : PCem ignore CR35 bit 7 et tire son horloge d'une table courte (`vid_et4000.c:406-419`) ; l'image
  sera juste, le rythme peut-être pas (annexe). `--menu-check` ne couvre pas l'ET4000 en 38h.
- **La phase 2 de boot-diff** ne rejoue pas `--type` (GR.4) : une divergence dans un banc tapé se localise mal.
- **Des comptes qui bougent** : GR.1c et GR.1e recomptent trois portes existantes et réécrivent six attendus ; le
  diff à g13b doit nommer chaque écart.
- **La durée** : un banc saisi dans DEBUG est long (BLTBANC, 410 s seul, VERIFICATION.md:12003-12004) ; six séances de
  plus dans la série.
- **Les images** : les bancs écrivent sur des copies (`--boot`, `par.sh`) ; l'incident du 03/10 ne peut pas revenir,
  mais un banc neuf joué à la main doit garder la même discipline.
- **La couverture** : une méthode inlinée n'a pas de listing ; seuls les compteurs comptent les branches.

## 4. Les décisions ouvertes

1. **La portée de la couverture.** GR.1 (04/10) dit « les cinq fichiers » ; le mode matériel est venu après (G13), et
   la décision n° 17 en fait le mode de l'utilisateur. Rien ne dit si les `.Materiel.cs` (53 méthodes) et le mode
   matériel entrent dans le compte. *Proposé : les dix fichiers, comptés dans les deux modes, un tableau par mode.*

Le reste suit des décisions prises : la fin dans le mode testé (PLAN.md:327-328), les bancs en C# seul dans les deux
modes (G13.9g, décision n° 17), les inconnus reproduits (n° 14), le 1024×768 puisque la ROM l'offre (GR.1).

## Annexe — Candidats, hors de la portée

- **L'entrelacé de l'ET4000.** `et4000_recalctimings` (`vid_et4000.c:385-430`) ne lit pas CR35 bit 7 (l'entrelacé
  vertical selon VGADOC, secondaire ; le data book, p. 111, à relire) ; les tables du mode 38h de la ROM ont le
  minutage du 8514 entrelacé (§ 1.5). Déduit ; à mesurer par GR.1c (CR35 relu).
- **L'horloge de l'ET4000.** Les sélections 2, 4, 6, 7 valent 36 MHz, 3 vaut 40, 5 vaut 65 (`:406-419`) ; aucune
  n'est 44,9 MHz, celle du 8514. Le générateur de la carte modélisée : inconnu.
- **La documentation.** PLAN.md:320-321 dit l'ET4000 « vérifiée jusqu'à Windows en 256 couleurs », et :324-326 que
  Windows tourne en VGA (pour GR.5).
